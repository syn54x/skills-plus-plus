# spp acts on GitHub content only from trusted authors, and pins the Verify block

`spp` acts mechanically on what it reads from GitHub: a verdict comment decides whether `spp merge` merges, the plan comment names the branch it merges into, a progress comment names the worker, and `spp verify` runs the Verify block's commands with `bash`. Until the panel on #267, it took the first **Marker comment** that started with the right marker, whoever wrote it, and ran the Verify block the issue body held at that moment. Anyone who can comment could then post a passing verdict before the reviewer did, and `spp merge` would merge an unreviewed slice; the reviewer's own write would fail, since GitHub refuses to let one user edit another's comment. Anyone who can edit an issue, which includes the outside reporter of a triaged bug, could swap a Verify line for `curl ... | sh` after the issue was approved, and the worker's `spp verify` would run it with the developer's credentials.

We draw one boundary. Comments and issue bodies are input that anyone may write; `spp` acts only on what a trusted author wrote, or on what a trusted author approved and pinned.

## Decisions

- **Whose Marker comments count.** `spp` reads a Marker comment (verdict, plan, progress, wave, or any other) only when its author is the current gh user or one GitHub marks `OWNER`, `MEMBER` or `COLLABORATOR` on the repository. Those three roles are people the repository's owners chose to let in, while anyone with a GitHub account can comment, so the line falls where a stranger's reach ends.
- **Skip, never stop.** An untrusted comment that starts with a marker is passed over as if it were plain text. The first trusted one is read and rewritten, and when there is none `spp` creates its own. A forged comment can therefore neither be read nor block the real writer, within the comment windows named under Not covered.
- **Every reader applies it.** The snapshot query fetches each comment's author, its association and the gh user in the same request, so `parseSnapshot` and `derive` stay pure. `markers.find`, `spp next`'s verdict history and `spp retro`'s wave read apply the same rule, and so does the epic board, which reads the wave comment through the snapshot's `wave`. The review gate runs the Verify block only through `spp verify`, so it never runs a block the pin does not match. `spp merge` re-reads the verdict comment through `markers.find` before it merges, so the merge rests on a check of the comment itself and not only on the snapshot that preceded it.
- **The Verify block is pinned from the agent's own file.** Hardening ends with `spp lint ticket <N> --pin <body-file>`, passing the file it just wrote to the issue. When the lint passes, the sha256 of that file's Verify block goes into the progress comment's trailer as `verifyPin`. The hash comes from the file, not from the issue as fetched, and the lint fails with `pin-match` when the two blocks differ, so an edit made between the agent's write and the pin is refused instead of approved. `spp verify` refuses to run, and records nothing, when the pin is missing or no longer matches the block, and tells the person to re-harden. The ready gate (`spp lint ticket <N>` without `--pin`) fails the same two cases, as `pin-present` and `pin-match`, so an unpinned or edited ticket never reaches `ready-for-agent`. After hardening, no skill runs a Verify block without one of those two checks first: a worker runs the ready gate at readiness and stops on a failure, `diagnosing-bugs` runs it before an issue's block becomes its loop, and the slice gate, `build` after each merge, and the panel for each closed Sub-issue run the block only through `spp verify`, stopping on a refusal. One module, `spp/src/pin.ts`, owns the pin's key, its hash and the lookup of the trusted progress comment, so the ready gate and `spp verify` cannot drift apart. The pin lives in a Marker comment, so the rule above protects it too. Triage re-pins only when its own step rewrote the body from its own file; otherwise harden's pin stands, since pinning the body as fetched would approve whatever anyone edited into it since.
- **A run speaks for `HEAD` only on a clean tree.** `spp verify` refuses to run when `git status --porcelain` is non-empty, so a `verified` note always describes the committed tree it is attached to.

## Considered options

- Refuse a Verify block whose last editor lacks write access: needs the issue's edit history on every run, and a block edited by a trusted person after approval would still run unreviewed.
- Trust anyone who can comment and rely on review to notice forged comments: a forged verdict merges before anyone reads it.
- Pass the gh user's login into `parseSnapshot` as a separate argument: one more `gh` call in every command that reads a snapshot, when the same query can return it.

## Not covered

Before a block is pinned, the agent itself runs untrusted commands by judgement: `triage` reproduces a bug from the reporter's steps, and `harden` runs the commands it is about to write on the base branch. The pin protects what happens after approval, not that first reading.

The pin covers the Verify block only. What to build, Acceptance criteria, Files owned, Interfaces and Test scenarios can still be edited after hardening, and a worker reads them as written, so an edit there can steer a worker without changing a command it runs.

The trusted roles are wider than write access. GitHub marks any member of the owning organization `MEMBER` on a public repository even without write access, and that member's Marker comments count. The current gh user is trusted too, so a prompt-injected worker running as the same gh user as the orchestrator could post a passing verdict on its own pull request; `spp merge` cannot tell that verdict from the reviewer's.

The snapshot looks for Marker comments in fixed windows: a pull request's first 30 comments, a Sub-issue's first 50 and the Epic's first 100. An outsider who posts enough comments before the real writer pushes the trusted comment out of its window, and `spp` then sees no verdict, progress or plan there. This can only hold a merge back, never force one: a missing verdict leaves the pull request `pr-open`, and nothing outside the window is ever read as trusted. Widening the windows or paging through them is a later change.
