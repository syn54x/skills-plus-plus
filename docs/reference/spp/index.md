## Modules

| Module | Description |
| ------ | ------ |
| [branch](branch.md) | `spp branch <epic> [--from <base>]` creates the Epic's integration branch `feat/<slug>` from `origin/<base>` (default `main`), pushes it, records it on the plan comment through `spp plan --branch`, and prints the branch name. When the branch exists it switches to it, and writes the plan comment only when the comment does not already name the branch, so a second run finishes whatever the first left undone. It has no `--json`. |
| [brief](brief.md) | `spp brief <issue> [--out FILE]` writes the worker brief for one Sub-issue and prints the file's path. The brief holds the ticket body verbatim, the Laws sources from the Routing block, the branch mechanics (cut from the Epic's integration branch, or from the default branch for a One-off) and the report format. Without `--out` the file goes in a new temporary directory. It has no `--json`. |
| [checks](checks.md) | `spp checks <pr \| sha> [--json]` reads CI for a pull request (its checks), or for a commit given as 7 to 40 hex characters (its check runs). It prints the result, followed by the failing or pending run names. The reading comes from each run's bucket, never from `gh`'s exit code: pending is never a pass, a cancelled run counts as a failure, and runs that all skip read as `none`. With `--json` it prints [Checks](checks.md#checks). |
| [claim](claim.md) | `spp claim <issue>` sets the Claim mark: it adds the `claimed` label, creating the label first when the repo lacks it, and prints nothing. The Claim mark is a label and never an assignee (ADR 0006). `spp unclaim` removes it. |
| [dispatch](dispatch.md) | `spp dispatch <issue> --driver bg\|desktop\|subagent` starts one worker on a Sub-issue that nobody holds, and refuses one held by the `claimed` label or an assignee. It has no `--json`. |
| [feedback](feedback.md) | `spp feedback check <body-file> [--title-file <file>]` is the outbound check on a skill-feedback draft that `/close-epic` proposes, run before anyone files it. The Routing block's `upstreamFeedback` profile sets what the draft may say. A blocked draft prints one `rule <rule> <name>, line <n>: <text>` line per hit on stdout. It never rewrites the draft. The title file holds one title per line, and a line that is only `owner/repo` names a repo. It has no `--json`. |
| [findings](findings.md) | `spp findings merge <file...> [--json] [--verdict <round> ...]` merges the review panel's Persona findings. Each file is one [PersonaFindings](findings.md#personafindings). Findings under 80 confidence are dropped, and findings on the same file, less than 5 lines apart and with the same normalised title become one that keeps the highest severity and every Persona. `--verdict` adds the panel's verdict over the merged list, as a last `Verdict:` line or, with `--json`, a `verdict` key; from round 3 a FIX FIRST is written HUMAN DECISION. With `--json` it prints [PanelFindings](findings.md#panelfindings). |
| [guard](guard.md) | `spp guard worktree` is the `PreToolUse` hook on Bash. In a session working in a linked worktree, it reads the command from the hook payload on stdin and denies one that would write into the main checkout outside that worktree; it allows the rest. It reads the command without running it: `$(...)`, variables and globs are not expanded, so they never deny. It has no `--json`. |
| [hand-back](hand-back.md) | `spp hand-back <issue> needs-info\|ready-for-human\|blocked --reason TEXT [--blocked-by <issue>]` returns a Sub-issue to a person or a queue in one call. It writes in this order: the progress comment (status `handed-back` with the route and reason), then the route label, then removes the Claim mark, so a failure part-way leaves the ticket held, never released without a route, and running the same call again finishes it. `--blocked-by` goes only with `blocked`, where it adds the blocked-by edge and keeps `ready-for-agent`; every other Hand-back removes `ready-for-agent`. It prints the progress comment's URL and has no `--json`. |
| [kind](kind.md) | `spp kind <issue> [--json]` says what an issue is: an Epic (it has Sub-issues), a ticket (it passes `spp lint ticket`) or raw (anything else), and why. `/build` routes on it. Without `--json` the answer is one line, such as `ticket: carries the ticket contract and one size`; with `--json` it prints [Kind](kind.md#kind). |
| [lint](lint.md) | `spp lint ticket <issue> [--json]` is the mechanical half of hardening. It checks the required sections, a fenced Verify block, Files owned lines starting `Create`, `Modify` or `Test`, Test scenarios shaped `<category>: ... → ...`, exactly one `size:` label, and no placeholder text. It prints `ok`, or one `<rule>: <detail>` line per failure; with `--json` it prints [LintResult](lint.md#lintresult). |
| [merge](merge.md) | `spp merge <pr> [--json]` merges a slice pull request into its Epic's integration branch, only when its gate passed on the current head, its blockers' pull requests have merged, its base is the integration branch and its checks pass. It merges with the Routing block's merge method (squash by default) pinned to the head the gate passed, then records the pull request on the wave comment. A conflict is never resolved here: the worker rebases. It prints `merged <pr> into <branch>` or `not merged: <reason>`; with `--json` it prints [MergeResult](merge.md#mergeresult). |
| [next](next.md) | `spp next <epic> [--json]` prints the build's next actions, one per line. The build loop is: run `spp next`, do what it says, run it again. It reads the Epic's preconditions, its state, CI on open pull requests, the gate's verdict history, the pull request to the base branch and the session list, all from GitHub and `claude`, never from local state. With `--json` it prints [NextActions](next.md#nextactions). |
| [note](note.md) | `spp note` keeps a local log of one-line notes, keyed by repo and Sub-issue, in spp's own state directory outside every repository: it appends a note, lists the latest notes of an Epic, or notes a hook event. |
| [plan](plan.md) | `spp plan <epic> [--goal TEXT] [--constraints TEXT] [--branch NAME] [--repos a/b,c/d] [--narrowed TEXT]... \| [--narrowed none] [--add-deviation TEXT] [--table-file FILE]` writes the Epic's `<!-- sdd-plan -->` comment, rewriting it in place, and prints its URL. A field you do not pass keeps its stored value. `--narrowed` replaces the stored list with every `--narrowed` of the call, `--narrowed none` clears it, and a call without it keeps it; `--add-deviation` appends to the Deviated list. The table file is copied in verbatim. It has no `--json`. |
| [preflight](preflight.md) | `spp preflight <epic> [--json]` checks the Epic's preconditions before a build, in order: `gh` 2.94 or later, the Epic open, at least one Sub-issue, a plan comment, and a Routing block in `CLAUDE.md` or `AGENTS.md`. It prints `ok: <check>` per passing check; at the first failure it prints `fail:` and `fix:` lines on stderr. With `--json` a pass prints the parsed [Routing](preflight.md#routing) block instead of the `ok:` lines. |
| [progress](progress.md) | `spp progress <issue> [--status S] [--worker TEXT] [--branch NAME] [--pr N\|URL] [--verify V] [--notes TEXT]` writes the Sub-issue's one `<!-- sdd-progress -->` comment, rewriting it in place, and prints its URL. A field you do not pass keeps its stored value. The comment's data trailer holds the fields (ADR 0007); a trailer that does not decode stops the write rather than erase the state. It has no `--json`. |
| [retro](retro.md) | `spp retro <epic> [--json]` collects the Epic's retro numbers from GitHub alone: findings by Law tag and by Sub-issue from the gate's verdicts, fix rounds, Hand-backs, the panel's rounds, and ponytail's hits. A pull request is a Sub-issue's when GitHub links it or the wave comment's trailer records it. An input it cannot read is named on stderr as `not found` and never counted as 0. With `--json` it prints [Retro](retro.md#retro); the field docs there say where each number comes from. |
| [status](status.md) | `spp status <epic> [--json]` prints every Sub-issue of an Epic with its state, grouped by Layer, from one GraphQL query. Each line is the ticket's state, its number and title, and its pull request when it has one; a blocking cycle gets a group of its own. With `--json` it prints the whole [EpicState](status.md#epicstate) instead. |
| [unclaim](unclaim.md) | `spp unclaim <issue>` clears the Claim mark: it removes the `claimed` label and prints nothing. A worker that stops without a pull request hands the ticket back with `spp hand-back` instead, which also records why. |
| [upsert](upsert.md) | `spp upsert <issue> <marker> <body-file>` writes a one-writer Marker comment, such as the Epic's summary or retro, verbatim and in place, and prints its URL. The body file's first line must be the marker; the comment gets no data trailer. It has no `--json`. |
| [verdict](verdict.md) | `spp verdict <pr> --ticket N --head SHA --spec pass\|fail --quality pass\|fail` records the slice gate's two verdicts as the pull request's `<!-- spp-verdict -->` Marker comment, rewritten in place, and prints its URL. It writes only while the pull request is still at `SHA`, because a verdict counts only on the head it was given on; when the head has moved it writes nothing and the reviewer reviews the new head. It has no `--json`. |
| [verify](verify.md) | `spp verify` runs a Sub-issue's Verify block and records the result on `HEAD`, and as a stop hook it holds a worker on an `sdd/*` branch until that record exists. It has no `--json`. |
| [wait](wait.md) | `spp wait <epic> [--interval SECONDS]` polls the Epic's state and the `claude` session list every interval (default 30 seconds) and exits when something changes, with one line per change: a ticket's state (`#12 claimed -> pr-open`) or one of its workers that stopped working (`t-12 done`). Run it in the background so its exit wakes the orchestrator. It has no `--json`. |
| [wave](wave.md) | `spp wave` plans the next Wave, and records waves, their pull requests and the review panel's rounds on the Epic's one `<!-- sdd-wave -->` comment. |
